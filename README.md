# Costez — full application

React 19 + TypeScript frontend, Java 21 / Spring Boot 3.5 backend, Flyway migrations, JDBC-backed login sessions, PostgreSQL deployment, and optional OpenAI / SMTP integrations. The frontend is served by the same Java process as the API. Gmail and Google sign-in are intentionally deferred.

## Run from this repository

Clone this repository and open its root folder. For a PostgreSQL deployment, create `.env` using `scripts/configure.ps1` on Windows or copy `.env.example` and set the database password and encryption key manually. Then run `docker compose up --build -d` and open http://localhost:8080. Create a workspace on the sign-in screen; demo seeding is disabled by default in Docker.

For a local build without Docker, install Java 21+, Node 24 and Maven 3.9+, then run `powershell -ExecutionPolicy Bypass -File build.ps1`. Launch `release/Start-Costez.cmd`. See the build and deployment sections below for Linux/macOS commands, HTTPS and integration configuration. The ready-to-run ZIP mentioned below is generated by `python scripts/package.py` after building; generated archives and binaries are not committed to this repository.

## Fastest way to present

1. Extract `Costez-Ready-To-Run.zip` into a writable folder.
2. Install Java 21 or newer if it is not already present. This machine has Java 23.
3. Double-click `Start-Costez.cmd`, or run `java -jar costez.jar`.
4. Open **http://localhost:8080** after the startup message appears.
5. Sign in with **demo@costez.local** / **CostezDemo2026!**.

This starts the complete frontend and backend, with a persistent embedded H2 database in `data/`. No Node, Maven, Docker, Google credentials, mail credentials or AI key are needed to run the packaged application. Keep the whole `data/` folder to preserve changes; stop the application before copying that folder. This local mode is for presentation and development. PostgreSQL is the deployment database.

Local mode creates `data/.mail-key` for encrypted queued mail. Include that file with local backups. PostgreSQL deployments require a stable `TOKEN_ENCRYPTION_KEY` (base64-encoded 32 random bytes); retain it privately with your backups. Changing it without migrating encrypted payloads makes queued emails unreadable.

Demo data is seeded once, using dates relative to first startup. Renewing tools and potentially unused tools remain useful in tomorrow's presentation. The expected initial monthly spend is ₹43,546.58 and flagged spend is ₹6,930 across Zoom, Adobe Creative Cloud and Mailchimp. Canva's annual invoice is normalized to integer paise. Loom is a demo detection awaiting review, excluded from totals. All demo names, invoices and owner email addresses are fictional.

## Working features

- Password registration and login, BCrypt password hashing, revocable server sessions persisted in the database, HttpOnly cookies, CSRF protection, login/pulse/report rate limits and a content security policy.
- Separate workspaces with tenant-scoped reads and writes. Each account owns one workspace in this release. Team invitations and workspace switching are not implemented.
- Subscription creation, editing, cancellation/reactivation and deletion; searchable filters; review confirmation; integer paise amounts; annual normalization; optimistic locking on subscription edits.
- Charge ledger, owner email and notes. Capability overlap works across categories (Zoom and Workspace both support video). Overlap is advisory, excluded from waste estimates. A missing last-use date does not imply non-use.
- CSV template and import, per-row rejection details, 1000-row / 2 MB limits, exact decimal parsing, imported records needing confirmation, file-hash deduplication.
- Real public owner-response links that work across devices against the same deployed server. Random 256-bit tokens, hashes stored in the pulse table, 14-day expiry, atomic single-use responses, no login needed. Queued email bodies containing response links are encrypted with AES-256-GCM. GET requests never consume tokens. SMTP is optional; when disabled, links and notifications can be demonstrated without sending emails.
- Domain CRUD, manual fallback, and real RDAP expiry lookup for .com, .net and .org. Lookup uses a fixed registry allowlist. Other TLDs stay manual.
- Daily 08:00 IST reminders for subscriptions at 30/15/7/1 days and domains at 60/30/14/7/1 days. A database queue records preview, pending, sending, sent and failed delivery states. Retry up to five times. At-least-once SMTP delivery can duplicate an email after a crash; it does not promise exactly-once delivery. Run one app instance for this release.
- Computed savings snapshots and print-to-PDF via the browser. Optional AI wording, with number verification and fallback. Daily limit: 10 reports/workspace.
- Workspace renaming, workspace JSON export, cascading account/workspace deletion, privacy information and integration status.
- Responsive ledger design, locally bundled specified fonts, keyboard-accessible Radix dialogs with focus trapping and Escape dismissal, light theme only.

## AI configuration

Set `OPENAI_API_KEY` only on the backend/server, and optionally `OPENAI_MODEL` (default `gpt-4.1-mini`). Restart the backend. Settings will show AI configured. Generate a report from Reports.

Only aggregate formatted amounts are sent to the OpenAI Responses API, with `store: false`. Tool names, owner names/emails, notes and email content are not sent. Financial arithmetic is computed in Java. AI text must use only provided numeric values; rejected, empty, timed-out or failed responses fall back to deterministic wording. The selected model must be available in your account. Real AI calls were not exercised without credentials; the no-key fallback and number validator are tested. [Official API quickstart](https://developers.openai.com/api/docs/quickstart).

PowerShell local example (set your own key privately, never commit it):

```powershell
$env:OPENAI_API_KEY = 'your-key'
$env:OPENAI_MODEL = 'gpt-4.1-mini'
java -jar costez.jar
```

## Email configuration

Set `MAIL_ENABLED=true`, `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_AUTH` and `SMTP_TLS`. Set `BASE_URL` to the URL recipients can reach, such as `https://costez.example.com`. New requests then enter the delivery queue. Existing PREVIEW rows remain previews; request another usage check after enabling SMTP. Email workers run every 30 seconds. Add real owner email addresses before sending; seed addresses end in `example.com`.

Amazon SES can supply SMTP credentials. Verify your sender and obtain permission to send to your intended recipients before using it. Mail provider setup is external configuration, not simulated delivery. Live SMTP delivery is unverified without credentials.

## Deploy with PostgreSQL

Requires Docker Engine and Docker Compose on the target machine. Docker is not installed on the development machine; the PostgreSQL API path is checked separately using a local PostgreSQL instance.

```sh
cp .env.example .env
# Edit .env: set a strong DATABASE_PASSWORD and TOKEN_ENCRYPTION_KEY.
# Generate TOKEN_ENCRYPTION_KEY using: openssl rand -base64 32
docker compose up --build -d
```

Open http://localhost:8080. Deployment defaults to **no demo account**. Create your workspace through the registration screen. Use `SEED_DEMO=true` only for a presentation deployment and choose a custom `DEMO_PASSWORD`. Set `ALLOW_REGISTRATION=false` after account provisioning if you want to close registration. Never expose the default local demo password on a public server.

On Windows, `powershell -ExecutionPolicy Bypass -File scripts/configure.ps1` creates `.env` with random database and encryption secrets. It refuses to overwrite an existing configuration. Then edit domain, base URL and optional integrations. Never commit `.env`.

For a domain with HTTPS:

1. Point DNS to the server; allow inbound ports 80 and 443.
2. Set `DOMAIN=costez.example.com`, `BASE_URL=https://costez.example.com`, and `COOKIE_SECURE=true` in `.env`.
3. Run `docker compose --profile https up --build -d`.

Caddy routes to the app and obtains TLS certificates. PostgreSQL has no public port; the app's direct port binds only to loopback. The app container runs as a non-root user. Persistent Docker volumes store PostgreSQL and Caddy state. `docker compose down` preserves data; do not use `down -v` if you need that data.

For a managed PostgreSQL service, configure `DATABASE_URL` as a **JDBC URL**, e.g. `jdbc:postgresql://host:5432/database?sslmode=require`, along with `DATABASE_USER` and `DATABASE_PASSWORD`. Flyway creates the application schema. Spring Session creates its session tables. A production database user must have the required schema creation permissions on first startup.

## Backups

JSON export is a readable application export, not a complete database restore format. For complete backups (including accounts, charges, pulses and sessions), use PostgreSQL dumps:

```sh
mkdir -p backups
docker compose exec -T postgres pg_dump -U costez -d costez -Fc -f /tmp/costez.dump
docker compose cp postgres:/tmp/costez.dump backups/costez.dump
```

Copy backups to durable storage outside the server and test restoration. To restore into an empty compatible database, copy the dump into the container and use `pg_restore -U costez -d costez /tmp/costez.dump`. Take a fresh backup before any replacement restore. Configure a daily cron/task scheduler around these commands if running beyond the presentation. Automatic S3 backup infrastructure is not provisioned by this repository.

## Build from source

Requirements: Java 21+, Maven 3.9+, Node 20.19+ or 22.12+ (Node 24 is used here). On Windows run `powershell -ExecutionPolicy Bypass -File build.ps1`. The script builds the frontend, copies it into backend resources, runs backend tests, and writes `release/costez.jar`. A downloaded workspace-local Maven is used if present; otherwise it uses installed Maven.

Manual commands:

```sh
cd frontend
npm ci
npm test
npm run build
cd ..
mkdir -p backend/src/main/resources/static
cp -r frontend/dist/. backend/src/main/resources/static/
cd backend
mvn package
java -jar target/costez-1.0.0.jar
```

For development, start the backend on 8080, then `npm run dev` in `frontend` to serve Vite on 5173 with API proxying. Use the same browser origin for sign-in and subsequent API requests. Session cookies do not need CORS exceptions.

CI (`.github/workflows/ci.yml`) builds and tests Java and TypeScript, then runs the live HTTP smoke test against PostgreSQL. If putting this folder inside a larger repository, place the workflow under that repository's `.github/workflows` and adjust working directories to `costez/`.

## Limits and deliberate architecture changes

Google sign-in and Gmail scanning are deferred as requested. Local password auth makes the app usable today; production verification and OAuth token handling are not falsely represented as complete. Receipt extraction, embeddings and forwarding-email ingestion are also deferred with that connector. Category/capability entry remains manual.

JDBC repositories are used instead of JPA, giving explicit SQL tenant filters and schema ownership. Hash routing avoids reverse-proxy route rewrites. Category bars use CSS and the renewal strip uses SVG. The visual style follows the provided design tokens and bundled fonts. Billing cycle advancement is manual: the app does not invent future invoices or usage activity.

This release supports one owner account per workspace, not team invitation/membership administration, password-reset emails, or SSO. Those are separate follow-up features. Horizontal scaling requires distributed scheduler coordination, shared rate limits and stronger queue leasing. SMTP delivery, OpenAI credentials and HTTPS certificates require real external configuration. A deployable build is provided; no cloud account resources or public deployment have been created.
